# Users API

HTTP API of the `users` microservice.

- Base URL (local): `http://localhost:8080`
- Base path: `/api/v1/users`
- Content type: `application/json`
- Authentication: user auth is **not wired yet** (cookie session comes from the dedicated
  auth service / gateway). Public endpoints are currently open, but mutating requests
  already require a CSRF token — see [CSRF](#csrf).
- Service-to-service calls use the separate `/internal/**` prefix and a shared secret
  header — see [Internal endpoints](#internal-endpoints).

Interactive documentation is generated by springdoc:

| UI | URL |
|----|-----|
| Swagger UI | `http://localhost:8080/swagger-ui.html` |
| OpenAPI JSON | `http://localhost:8080/v3/api-docs` |

## CSRF

Browser clients authenticate with a cookie session, so all mutating requests
(`POST`, `PUT`, `PATCH`, `DELETE`) must carry a CSRF token:

1. Any safe request (for example `GET /api/v1/users`) sets an `XSRF-TOKEN` cookie.
2. Send that cookie back and add its value as the `X-XSRF-TOKEN` header:

```bash
curl -i -X POST http://localhost:8080/api/v1/users \
  -H 'Content-Type: application/json' \
  -H "X-XSRF-TOKEN: $CSRF_TOKEN" \
  -b "XSRF-TOKEN=$CSRF_TOKEN" \
  -d '{"firstName":"John","lastName":"Doe","email":"johndoe@gmail.com","location":{"countryCode":"ES","city":"Madrid"}}'
```

A missing or invalid token is rejected with `403` before the request reaches a
controller. The `curl` examples below omit the header for brevity; add it when calling
the API from a cookie-authenticated client.

## The user object

```json
{
  "id": "f626f698-1659-480d-9997-f982bd5de144",
  "firstName": "John",
  "middleName": null,
  "lastName": "Doe",
  "email": "johndoe@gmail.com",
  "location": {
    "countryCode": "ES",
    "city": "Madrid"
  },
  "status": "ACTIVE"
}
```

| Field                 | Type   | Notes                                                              |
|-----------------------|--------|--------------------------------------------------------------------|
| `id`                  | UUID   | Generated by the service on create, never by the client            |
| `firstName`           | string | Required on create, `max 255`                                       |
| `middleName`          | string | Optional, `max 255`                                                 |
| `lastName`            | string | Required on create, `max 255`                                       |
| `email`               | string | Required on create, `max 255`, valid address; trimmed and lowercased; unique |
| `location.countryCode`| string | Required on create, `max 255`                                       |
| `location.city`       | string | Required on create, `max 255`                                       |
| `status`              | enum   | Server-managed: `ACTIVE`, `INACTIVE`, `SUSPENDED`, `BLOCKED`, `DELETED` |

## Endpoints

### List users

```
GET /api/v1/users
```

`200 OK` — array of user objects (empty array when there are none). No pagination yet.

```bash
curl http://localhost:8080/api/v1/users
```

### Get a user

```
GET /api/v1/users/{id}
```

| Status | When |
|--------|------|
| `200`  | user found |
| `400`  | `id` is not a UUID |
| `404`  | no user with this id |

```bash
curl http://localhost:8080/api/v1/users/f626f698-1659-480d-9997-f982bd5de144
```

### Create a user

```
POST /api/v1/users
```

Request (any of `firstName`, `lastName`, `email`, `location` may be omitted here —
the application layer answers `400` with a readable message):

```json
{
  "firstName": "John",
  "middleName": null,
  "lastName": "Doe",
  "email": "johndoe@gmail.com",
  "location": { "countryCode": "ES", "city": "Madrid" }
}
```

`201 Created` — the created user, including `id` and `status: "ACTIVE"`.

| Status | When |
|--------|------|
| `201`  | created |
| `400`  | missing required field, invalid email, field too long, malformed body |
| `409`  | a user with this email already exists |

```bash
curl -i -X POST http://localhost:8080/api/v1/users \
  -H 'Content-Type: application/json' \
  -d '{"firstName":"John","lastName":"Doe","email":"johndoe@gmail.com","location":{"countryCode":"ES","city":"Madrid"}}'
```

### Update a user

```
PUT /api/v1/users
```

Only `email` and `location` can be changed. `firstName`/`middleName`/`lastName` are
accepted by the payload but **ignored**. `id` must be present in the body.

Request:

```json
{
  "id": "f626f698-1659-480d-9997-f982bd5de144",
  "email": "john.new@mail.com",
  "location": { "countryCode": "PT", "city": "Lisbon" }
}
```

Both `email` and `location` are optional; omit a field to leave it unchanged.

`200 OK` — the updated user.

| Status | When |
|--------|------|
| `200`  | updated |
| `400`  | `id` missing, invalid email, field too long, malformed body |
| `404`  | no user with this id |
| `409`  | the user is not `ACTIVE` (only active users can be edited) |
| `409`  | the user was modified concurrently (optimistic lock), retry the request |

### Delete a user

```
DELETE /api/v1/users/{id}
```

Physical delete of the row.

| Status | When |
|--------|------|
| `204`  | deleted |
| `400`  | `id` is not a UUID |
| `404`  | no user with this id |

```bash
curl -i -X DELETE http://localhost:8080/api/v1/users/f626f698-1659-480d-9997-f982bd5de144
```

### Status transitions

All four transition endpoints return `204 No Content` on success and share the same
error contract: `400` for a malformed id, `404` for an unknown user, `409` for a
transition that is not allowed from the current status.

| Endpoint                          | Target status | Allowed from                      |
|-----------------------------------|---------------|-----------------------------------|
| `PUT /api/v1/users/{id}/block`     | `BLOCKED`    | `ACTIVE`, `INACTIVE`, `SUSPENDED` |
| `PUT /api/v1/users/{id}/suspend`   | `SUSPENDED`  | `ACTIVE`                          |
| `PUT /api/v1/users/{id}/unblock`   | `ACTIVE`     | `INACTIVE`, `SUSPENDED`, `BLOCKED`|
| `PUT /api/v1/users/{id}/reactivate`| `ACTIVE`     | `INACTIVE`, `SUSPENDED`, `BLOCKED`|

`unblock` and `reactivate` are the same transition (`→ ACTIVE`).

Full transition matrix (`✓` = allowed):

| from \ to   | ACTIVE | INACTIVE | SUSPENDED | BLOCKED | DELETED |
|-------------|:------:|:--------:|:---------:|:-------:|:-------:|
| `ACTIVE`    | ✗      | ✓        | ✓         | ✓       | ✓       |
| `INACTIVE`  | ✓      | ✗        | ✗         | ✗       | ✓       |
| `SUSPENDED` | ✓      | ✗        | ✗         | ✓       | ✓       |
| `BLOCKED`   | ✓      | ✗        | ✗         | ✗       | ✓       |
| `DELETED`   | ✗      | ✗        | ✗         | ✗       | ✗       |

`INACTIVE` and `DELETED` are valid statuses in the domain, but no endpoint currently
moves a user into them (see [decisions](../decisions.md#open-questions)).

```bash
curl -i -X PUT http://localhost:8080/api/v1/users/f626f698-1659-480d-9997-f982bd5de144/block
```

Blocking an already blocked user:

```json
{
  "timestamp": "2026-11-17T07:39:51.061902757Z",
  "status": 409,
  "error": "Conflict",
  "message": "Cannot transition from BLOCKED to BLOCKED",
  "path": "/api/v1/users/f626f698-1659-480d-9997-f982bd5de144/block"
}
```

## Errors

Every error response has the same shape:

```json
{
  "timestamp": "2026-11-17T07:39:44.775161879Z",
  "status": 404,
  "error": "Not Found",
  "message": "User not found: 00000000-0000-0000-0000-000000000000",
  "path": "/api/v1/users/00000000-0000-0000-0000-000000000000"
}
```

| Status | Meaning                                                             |
|--------|---------------------------------------------------------------------|
| `400`  | validation failure, type mismatch, malformed body                   |
| `401`  | missing credentials on an internal endpoint                         |
| `403`  | missing/invalid CSRF token, or insufficient privileges              |
| `404`  | unknown user or unknown route                                       |
| `405`  | HTTP method not supported for the route                             |
| `409`  | duplicate email, invalid status transition, concurrent modification |
| `415`  | unsupported `Content-Type`                                          |
| `500`  | unexpected error; the message is always the generic reason phrase   |

Internal details (SQL errors, stack traces, exception messages) are logged only and
never returned to the client.

## Internal endpoints

Service-to-service handlers live under `/internal/**` and use a separate, stateless
security chain. Each request must include the shared secret:

```
X-Internal-Token: <INTERNAL_SERVICE_TOKEN>
```

Missing or invalid values return `401` with the standard `ApiError` body. CSRF is not
required on this prefix. The token is compared in constant time and is never logged.

This prefix must not be exposed through the public ingress, and the gateway must strip
any client-supplied `X-Internal-Token` header before forwarding requests. The secret is
read from `ORDERLY_INTERNAL_TOKEN` (Compose: `INTERNAL_SERVICE_TOKEN`); the service
refuses to start without it. Treat it like a password and rotate it by updating every
caller.

No internal handlers exist yet — the prefix is reserved and protected in advance.

## Versioning

The API is versioned by path segment (`/api/v1`). Breaking changes get a new version;
additive changes do not.
